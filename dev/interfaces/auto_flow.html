Automatic Pipelines#

dipy_auto runs a whole diffusion pipeline from a single command. A pipeline is a list of stages described in a TOML file; each stage names a DIPY command line workflow and how its inputs connect to the outputs of the stages before it. Four pipelines ship with DIPY, from preprocessing alone to a full preprocessing, reconstruction, tracking and bundle segmentation chain.

Name

Stages

preprocessing

Denoising, Gibbs unringing, motion and bias field correction, reslicing, b0 extraction, brain mask: the preprocessing of full

dti_only

Denoising, brain mask, DTI fit and tensor metrics

tractography

Denoising, brain mask, DTI and CSD fits, tracking

full

Full preprocessing with motion correction, T1 registration to the b0, DTI and FORCE fits, tracking, SLR to an atlas, RecoBundles, bundle labelling, BUAN profiles

Every pipeline denoises with dipy_denoise, which picks Patch2Self, MP-PCA or NLMeans from the number of volumes, of diffusion directions and the SNR of the data.

full runs when neither --pipeline_type nor a configuration file is given. dipy_auto --list_pipelines lists the pipelines with their description; it shows full only, unless it is run with --log_level DEBUG.

One set of images#

Pass the diffusion image and its gradient table; the file types are recognised from their extensions:

dipy_auto dwi.nii.gz dwi.bval dwi.bvec --pipeline_type preprocessing \
    --out_dir results

Add the companion images the pipeline needs:

dipy_auto dwi.nii.gz dwi.bval dwi.bvec --t1_file t1.nii.gz \
    --mask_file brain_mask.nii.gz --out_dir results

In full, the T1 image is registered rigidly to the mean b0, giving t1w_dwispace.nii.gz and its transform t1w_to_dwi_affine.txt; without --t1_file that stage is skipped and the rest of the pipeline runs as usual. A mask given with --mask_file must be binary and cover at least a quarter of the volume. It replaces the output of every stage that computes a brain mask, and those stages are skipped. Pipelines with dipy_slr or dipy_recobundles stages download the HCP 30-bundle atlas on their first run, unless --atlas_tractogram and --bundle_atlas_dir point at another atlas.

--dry_run prints the execution plan, the stage order and an estimate of the disk space the run needs, without executing anything. The run stops before the first stage if the output directory lacks that space.

A stage whose outputs are all already on disk is skipped, so re-running a command after a failure picks up where it stopped. --force runs every stage again and overwrites its outputs. --start <stage> skips every stage before <stage> without checking for its outputs, and reads them from disk; use it to re-run the later stages of a pipeline with different parameters.

--interactive_mode inspects the b-values, suggests a pipeline and offers to build one stage by stage.

Each run writes, into --out_dir:

  • <timestamp>_<pipeline>_pipeline.toml, the exact configuration that ran, unless the run was started from a configuration file;

  • <timestamp>_dipy_auto.log, the full log;

  • <timestamp>_pipeline_report.html, the final report;

  • reports/NN_<stage>.html and reports/index.html, the per-stage QC pages, refreshed as soon as each stage finishes.

Reopen a report, with its images served so the QC buttons work:

dipy_auto results/20260929_120000_pipeline_report.html

Writing a pipeline#

Start from the configuration a run wrote, or from scratch. A configuration has an optional [General] table, an [io] table of input paths and one [[pipeline]] table per stage:

[General]
name = "my_dti"

[io]
dwi = ""
bvals = ""
bvecs = ""
out_dir = "."

[[pipeline]]
name = "denoise"
cli = "dipy_denoise"
input_files = ":math:`{io.dwi}"
bvalues_files = "`{io.bvals}"

[[pipeline]]
name = "brain_mask"
cli = "dipy_median_otsu"
input_files = ":math:`{denoise.out_denoised}"
bvalues_files = "`{io.bvals}"
save_masked = true

[[pipeline]]
name = "dti_fit"
cli = "dipy_fit_dti"
input_files = ":math:`{denoise.out_denoised}"
bvalues_files = "`{io.bvals}"
bvectors_files = ":math:`{io.bvecs}"
mask_files = "`{brain_mask.out_mask}"
out_dir = ":math:`{io.out_dir}/dti"

Every key of a stage other than name and cli is an argument of the workflow behind cli, under the same name as its command line option. `{io.<key>} reads the [io] table, and :math:`{<stage>.<output>} reads the file a previous stage wrote for one of its out_* arguments, or its out_dir. These references alone set the execution order: stages run in dependency order, whatever their order in the file.

dipy_median_otsu computes the mask from the b0 volumes it finds with bvalues_files. Without b-values it needs vol_idx, the indices of the volumes to use, as a 4D image has no single volume to segment.

A stage with optional = true runs only when every [io] entry it references has a value. Otherwise it is skipped, shown as such in the reports, and so is every optional stage that reads its outputs; a stage that is not optional and reads them stops the run before it starts. This is how full registers the T1 image only when one is given:

[[pipeline]]
name = "t1_registration"
cli = "dipy_align_affine"
static_image_files = "`{b0_extraction.out_b0}"
moving_image_files = ":math:`{io.t1w}"
transform = "rigid"
optional = true

Run it with:

dipy_auto my_dti.toml dwi.nii.gz dwi.bval dwi.bvec --out_dir results

The files on the command line fill the [io] table, so one configuration serves many subjects. Before any stage runs, dipy_auto stops on an input file that does not exist, then on an unknown command, a misspelled or missing argument, a reference to a stage or output that does not exist, or a dependency cycle, listing every problem of the configuration at once. When several stages would write a file of the same name in the same directory, each of those outputs is renamed after its stage, for instance pam_csd_fit.pam5, and the configuration is saved with the new names.

A whole BIDS dataset#

With --bids, dipy_auto follows the BIDS-App argument convention and runs the pipeline on every diffusion acquisition of a dataset:

dipy_auto /data/ds001 /data/ds001/derivatives/dipy participant --bids \
    --pipeline_type preprocessing

The positional arguments are the dataset root, the output directory (optional) and the analysis level (optional; only participant is implemented). When the output directory is omitted, the results go to <bids_dir>/derivatives/dipy. --bids_folder passes the dataset root as an option instead, which is convenient together with a TOML configuration:

dipy_auto my_pipeline.toml --bids --bids_folder /data/ds001

Restrict what runs with the entity filters, which accept labels with or without their prefix:

dipy_auto /data/ds001 --bids --participant_label 01 02 --session_label 1
dipy_auto /data/ds001 --bids --acquisition_label b1000 --run_label 1

For every acquisition, dipy_auto resolves from the dataset:

  • the b-value and b-vector files and the JSON sidecar, following the BIDS inheritance principle, so that metadata placed at the dataset, subject or session level applies to the files below it;

  • the T1w image of the subject, preferring the same session;

  • the EPI fieldmap acquired with the opposite phase encoding, by IntendedFor, then by an opposite dir- entity, then by an opposite PhaseEncodingDirection;

  • PhaseEncodingDirection, TotalReadoutTime, EffectiveEchoSpacing, EchoTime and RepetitionTime, which are logged and stored in the [io] section of the generated configuration as `{io.pe_dir}, :math:`{io.total_readout_time}, `{io.effective_echo_spacing}, :math:`{io.echo_time} and `{io.repetition_time}.

Everything that was inferred is reported in the log, so a run can be checked against what the dataset actually contains.

Output layout#

The output is a BIDS-Derivatives dataset:

derivatives/dipy/
    dataset_description.json
    <timestamp>_batch_summary.html
    <timestamp>_batch_summary.json
    <timestamp>_dipy_auto.log
    sub-01/
        dwi/
            <timestamp>_<pipeline>_pipeline.toml
            <timestamp>_pipeline_report.html
            reports/index.html
            dwi_denoised.nii.gz
            sub-01_desc-denoised_dwi.nii.gz
            sub-01_desc-denoised_dwi.json
    sub-02/
        ses-1/
            dwi/
                acq-b1000_dir-AP_run-1/
                acq-b1000_dir-AP_run-2/

Every acquisition gets its own directory, so the per-stage QC reports and the resume logic work per acquisition exactly as they do for a single subject. When one session holds several acquisitions they would share a datatype directory and overwrite each other, so each one is given a subdirectory named after the entities that tell them apart.

Headline outputs — FA, MD, RD and AD maps, the denoised DWI, the brain mask and tractograms — are additionally exposed at the datatype level under BIDS-style names such as sub-01_desc-FA_dwimap.nii.gz, each with a JSON sidecar recording the stage and the source files. These are links to the stage outputs, which are left where the pipeline wrote them.

The batch summary lists every acquisition with its status, duration, the stage it failed at if it failed, and a link to its report. A failing acquisition does not stop the batch — dipy_auto reports it, carries on, and exits non-zero at the end. --stop_on_error stops at the first failure instead.

Validation#

dipy_auto refuses to guess. A dataset root passed without --bids is an error naming the command to use instead, and single-subject inputs such as a positional DWI file or --t1_file cannot be combined with --bids, since they would be ambiguous over a whole dataset.

If pybids is installed, the file names of the discovered acquisitions are checked against the BIDS validator and any non-compliant name is reported as a warning. The discovery itself never depends on pybids, so the BIDS mode works without it.
